# Friends to Amigos release notes standard

This file defines the required format for product release pages published from `main`.

## Scope

Use this format for every user-facing Friends to Amigos release created from `main`, including stable releases and test/beta APK releases where a GitHub Release page is created.

Do not publish a release with only a short autogenerated commit list. Release notes must explain the user-facing product changes in clear language.

## Required release-page structure

# Friends to Amigos vX.Y.Z

Write a short 1–3 paragraph summary explaining what this release is about, who it benefits, and the most important changes.

## Download the application

Tell the user to download the APK attached to the GitHub Release under **Assets**. If multiple APKs exist, explain which one normal Android users should install.

Include any minimum Android version or architecture requirement if it changed.

## Installation and first launch

Include only information that is genuinely relevant to the release, such as:

- whether the existing app can be updated in place;
- whether uninstall/reinstall is required;
- whether user progress/settings are preserved;
- Android's unknown-apps prompt for sideloaded APKs;
- any migration, permission or first-launch step users should expect.

Do not invent installation warnings that do not apply.

## New in vX.Y.Z

This is the main changelog and should be detailed and scannable. Group changes by product area rather than presenting a raw commit list.

Use the categories that apply, for example:

### Learning and course content
- New levels, units, lessons, explanations, exercises or curriculum changes.
- Corrections to Spanish content and improvements to teaching quality.

### Games
- New games, question banks, randomisation, difficulty changes, feedback or scoring improvements.

### Writing and assessment
- Writing-engine improvements, better error diagnosis, spelling/grammar/conjugation feedback, or free-writing changes.

### UX and navigation
- Home-screen changes, navigation, buttons, keyboard behaviour, progression flow, accessibility and visual improvements.

### Audio, listening and speaking
- Listening/speaking lesson changes, playback improvements, question additions and limitations that matter to users.

### Reliability and technical improvements
- Performance, offline behaviour, persistence, build changes, compatibility, dependency or architecture work that has a user-visible benefit.

### Bug fixes
- Specific bugs fixed in this release. Describe the symptom and result rather than only naming an internal file or ticket.

Do not force empty headings into a release. Use only the sections that contain meaningful changes.

## Previous release highlights

When useful, include concise sections such as:

### New in vX.Y
- Important changes from that release.

### New in vX.W
- Important changes from that release.

This section exists to give users useful context, similar to a cumulative product-update page. Keep the current release much more detailed than older entries so the page does not become unmanageably long.

## Known issues and limitations

List only current, confirmed issues or limitations that users may encounter. Include workarounds when one exists.

If there are no known user-facing issues worth calling out, omit this section rather than writing filler.

## Release-writing rules

- Base the notes on the actual diff, merged work, version history and tested behaviour on `main`.
- Never claim a feature, fix or compatibility improvement that is not present in the release.
- Prioritise user-facing behaviour over implementation details.
- Be detailed enough that a tester can understand what changed without reading commits.
- Use short paragraphs and grouped bullets so the page is easy to scan on a phone.
- Use plain English and explain technical terms when users need to understand them.
- Mention regressions, migrations or limitations clearly rather than hiding them.
- Do not use a raw Git commit log as the release page.
- Keep the title/version consistent with the app's actual version.

## Before publishing a release from main

1. Confirm the intended version number.
2. Compare the release commit/tag with the previous release point.
3. Identify all meaningful user-facing changes.
4. Run the project's required checks/tests/builds.
5. Confirm the APK to attach/download is from the release commit on `main`.
6. Write the GitHub Release page using this standard.
7. Include known issues or upgrade notes where relevant.
8. Publish the release only after the notes match the shipped build.
